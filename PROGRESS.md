# Progress Log

Development progress log for claude-config. Tracks implementation milestones across PRD work.

## [Unreleased]

### Added

- (2026-08-04) Got the first real measurement of how often Claude stops to ask for permission: 16 interruptions across 182 tool calls in about seven and a half hours, roughly one in eleven. Reporting it as a rate rather than a count matters, because the recorder also logs every command that ran, which is what makes a before-and-after comparison possible once a setting changes. The largest single category was multi-line blocks of Python or test code written straight into the shell — every one of which could have been written to a file and run plainly, with no interruption. Treat the shape of this as one day of one kind of work rather than a picture of normal use; the rate is the part worth comparing against later.

- (2026-08-03) Added `scripts/measure-context-load.sh`, which reports what actually loads into a Claude Code session at startup — every rule file and skill, how it got there, what it costs in bytes, and whether it survives a context compaction. The numbers are checked against Claude Code's own account of what it loaded rather than inferred from file contents, using a hook that reports each file and the reason it was pulled in. That check caught two things guessing would have missed. The rules index was loading into every single session, costing about 3,100 tokens — the entry below dated 2026-08-02 claims it "costs nothing where it now lives and is read on demand," and that claim was wrong. Moving the index out of the always-loaded config file had moved it from one always-loaded location to another. The check that exists to catch exactly this mistake had been told to skip that file, on the grounds that it is never loaded. Separately, an always-loaded file living outside this repository had been missing from every previous count.

- (2026-08-03) Added a test suite for the context-load measuring script, which had shipped without one. Twenty-seven tests, each building a small throwaway config tree and running the real script against it rather than standing in a fake. Two are guards against defects the script actually had, and both were checked by reintroducing the defect and confirming the test goes red — a test written after the fact can pass for the wrong reason. The script now accepts a directory to measure, which is what lets the tests point it somewhere harmless; run with no arguments it behaves exactly as before, and no test ever writes to the real inventory.

- (2026-08-03) Settled by measurement whether the rule files that are meant to load in every session actually come back after a long conversation gets summarized to free up room. They do. The question mattered because every one of those files reaches the session indirectly, by being referenced from the main config file rather than living in it, and the official documentation lists what survives summarization without mentioning referenced files at all. The measurement also explains why other people have concluded the opposite: the tool reports the two main config files as restored, but reports each referenced file as merely "included," pointing back at its parent. Anyone looking only for the first label sees two files and reasonably concludes the rest were dropped. The same run confirmed the other half, which is the more useful half — a rule scoped to load only for certain file types genuinely does vanish when the conversation is summarized, and stays gone until someone opens a matching file again. So keeping a rule available for a whole session costs context in every session, with no way to have both.

- (2026-08-03) Established that a skill's instructions are cut off after roughly 5,000 tokens when a long session compacts, keeping the beginning of the file and dropping the end. Eight skills are over or near that limit, including several whose final steps — merging, cleanup, verification — are the part that disappears. Where an instruction sits inside a skill file is therefore a matter of correctness rather than tidiness, which changes how the planned skill consolidation has to be written.

- (2026-08-03) Discovered that per-project skills do not override personal ones — it works the opposite way round, and the opposite way round from how rules behave. The practical consequence is that a command for switching a project into autonomous mode has not been switching the skills since March. Nine repositories were set up that way and all nine have been running the ordinary interactive skills. The command was not doing nothing: the parts of it that adjust settings worked fine, so those repositories have been running an automated loop driving skills that stop and wait for a human answer. Verified by running a real session in one of the affected repositories and asking it which version it had loaded, rather than reasoning from the file layout, which looks exactly like a working override.

- (2026-08-03) Cloned every reference repo the claude-config workflow audit needs, then pruned the set twice before treating it as final. Three of Viktor Farcic's repos, and Michael Forrester's list re-run live (he'd grown from 20 to 60 public repos in a day) and judged by name/description against whether it plausibly holds coding-agent configuration, plus Whitney's own second config repo `claude-personal`. Seven of Michael's repos survived both passes. The two-stage prune matters more than the specific count: guessing from a repo's name costs nothing but proves nothing, and this audit's later findings depend on the source material actually being relevant.

- (2026-08-02) Documented a third approval-prompt trigger class: a command that changes directory before running `git` is blocked because it can execute untrusted hooks from the target directory. The avoidance is narrow — never `cd` inside a shell call, use `git -C`, skip `&&` chains, and prefer the dedicated file tools.

- (2026-08-02) Adopted "one decision, two places" as the organizing principle for the claude-config redesign spec. Five independent instances surfaced during scoping. The spec will now open with an inventory of every coupled pair in the system and organize its decisions by remedy — collapse the second location, derive one artifact from the other, or assert a check on divergence — in that order of preference, with every "assert" justified by why the stronger two remedies were rejected. The repo audit also gained a requirement to design a hook that warns when one half of a pair is edited, deriving its pair list by construction rather than maintaining a list that would itself be a second place a decision lives.

- (2026-08-04) Started recording permission prompts as they happen, using two notification points that ship with Claude Code but appear in none of its documentation — one that fires as a prompt is about to be shown, carrying the exact rule the interface is about to offer as "always allow this," and one that carries the reason for a refusal. ### Changed

- (2026-08-04) Turned three separate slips into one question the audit now has to answer. A rule gets written down, agreed to, and then ignored — it has happened three times in this work: how shell commands get composed, an instruction about not interrupting Whitney, and writing the test before the code rather than after. Each one was already documented somewhere Claude reads every session. The useful comparison is sitting in the same repository: a rule requiring a header comment on every code file is enforced by a check that refuses the edit, and it does not get violated, while the rules enforced by prose do. So the open question is no longer where to file the guidance, it is what makes a rule stick at all. Deliberately not answered yet — two practitioners whose setups this project is already studying may have solved it, and adopting a working answer beats inventing one. That also reopened a judgment call: a repository about agent governance was set aside earlier as containing no relevant configuration, which was true of the question being asked then and may not be true of this one.

- (2026-08-04) Refocused the approval-friction research around the question actually worth answering: how do other people run Claude Code for hours without it stopping to ask them things, when that is not possible here? The research had been scoped to trimming individual interruptions out of the current setup, which is a smaller question with a different answer — the mode a session runs in plausibly matters more than any list of pre-approved commands, and nothing in the plan was checking that. The work now splits in two. A short pass reads the official documentation on the available modes and proposes one reversible change to try this week, measured against the newly installed recorder. The durable version stays with the later research stage, which re-reads the same documentation and treats any answer that changed in the interval as a finding in its own right, since this tool moves fast enough that research done weeks before a decision is not safe to trust. How other practitioners handle it is now a named question the comparison research has to answer, aimed at their committed configuration rather than at what they write about it.

- (2026-08-03) Restructured the claude-config workflow audit into four ordered stages — measure what exists, research what is possible, decide what to build, then clean up and verify. The plan had been interleaving the three, so design decisions were scheduled before the research meant to inform them: a policy for classifying every rule was due second of nine steps, before any of the comparison research had run. Design now has a stage of its own, where it happens as a conversation rather than as a side effect of writing something else. Reading the documentation to find out what the tool can actually do became a first-class piece of research alongside the two workflow comparisons, because nearly every finding that changed the plan this week came from reading documentation rather than reasoning about it. Renaming the stages was done with a script after noticing that a careless find-and-replace would have quietly rewritten references belonging to a different, older plan into the new names — producing text that reads correctly and says something false.

- (2026-08-04) Wrote down two shell traps that cost real debugging time this week, so the next person meets them as documentation rather than as a wrong answer. Ending a pipeline with a "quiet" search is unsafe when the script is set to fail on any pipeline error: the search stops reading the moment it finds a match, the command feeding it is killed mid-write, and the pipeline reports failure even though the match succeeded. It only bites once the input grows past a buffer size, so it ships looking fine. Separately, a common shorthand for "whitespace" in search patterns is a GNU extension that the `grep` shipped with macOS reads as a literal letter s — silently, and in the direction that fails on the laptop while passing in CI. Also recorded, in the testing notes, that a passing test is not evidence a test can fail, along with the two ways a check of that kind can itself go wrong.
