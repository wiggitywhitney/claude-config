- (2026-08-05) Added `scripts/audit-enumerate.sh`, which lists what this configuration actually contains — every hook, every skill, every pair of files that encode one decision in two places, and every repository under the configured search root carrying Claude Code configuration. Each list comes out as one machine-readable record per line, so the tables in the audit write-up are generated from it rather than typed by hand. The reason for a script rather than looking around is that a person or a model sweeping a directory cannot be checked; anyone can re-run this and get the same answer. Its first run against the real repository was wrong five times over, and both causes were invisible from reading the code: a script path written inside a skill's instructions points at that skill's own folder rather than the top of the repository, and a pattern matching a short path also matches the end of a longer one, so four working references and one fully-spelled-out path were all reported broken. Both are now covered by tests that fail without the fix. Every one of the original "broken reference" findings turned out to be the checker's fault rather than the repository's, which is the argument for running a check against reality before believing what it says.

- (2026-08-05) Fixed four copies of a code-review command that had been failing on an option the tool dropped months ago, and found that the same fix had already been applied to two other copies without anyone checking the rest. Six places in this project state that one command. The rules file and the script the push-time check actually runs were both correct — that script was repaired three days earlier, when the push-time review was found to have been quietly doing nothing. Its duplicate, sitting in a skill's own scripts folder, was never touched and still carried all four bad options. Two things make this worse than a stale command. The failure prints "skipping," which is the same word used when the tool is not installed, so a broken review and a legitimately absent one look identical to a reader. And the history shows this is not a one-off: the same option was removed from the same skill on three separate days in June, each time in a different copy. All four remaining copies are now correct, which fixes today's instance and nothing structural — the real repair is for no skill to state the command at all, since the rules file that has it right is already loaded in every session.

- (2026-08-05) Fixed two tools that each decide whether a rule file is pulled in unconditionally, and had been deciding it differently. One required the filename to end where the reference ends; the other did not, so a reference to a backup copy of a file counted as a reference to the file itself in one tool and not the other. The visible consequence is that a correctly configured rule could be reported as misconfigured, on the strength of some unrelated longer filename that happens to start the same way. The interesting part is where it was hiding: two separate pieces of code answering one question, drifting apart with nothing to notice, inside the very tooling built to find that pattern elsewhere in this configuration. Both now agree, with a test that fails without the fix. Worth saying plainly that this is the weaker repair — one shared implementation would remove the possibility of drift, and two implementations that currently agree only removes today's instance.

- (2026-08-04) Added `scripts/measure-prompt-rate.sh`, which turns the raw log of permission interruptions into a rate: interruptions per hundred tool calls, split by the mode the session was running in and by the shape of the command that triggered them. It replaces reading the log by eye, and the reason that matters is not tidiness. The first hand-read of the same data produced a confident, internally consistent, completely wrong conclusion — a pattern-match written to catch mode names silently ignored the one that had a capital letter in the middle, which happened to be the majority of the records. The script carries a test for that exact mistake, and another for a second one found by running it: passing the log's file path into a text-processing tool under the name `log` collided with that tool's own logarithm function and printed `-inf` where the filename should have been. Both were caught the same day they were made.

- (2026-08-04) Established, by measuring rather than reasoning, that how strict Claude's permission setting is does not explain how often it interrupts. Across nine and a half hours, the stricter setting that reviews every action interrupted on six percent of tool calls, and the looser setting that pre-approves file edits interrupted on nine percent — the loose one was worse. That reads as a contradiction until you look at what the loose setting actually widens: file edits and a handful of file-shuffling commands, and nothing else. Every other shell command stays on the same path it was always on. So a multi-line block of Python typed into the shell gets stopped identically under both. The useful conclusion is that loosening the setting was never the fix, because the interruptions were not coming from strictness.

- (2026-08-04) Documented the six permission settings Claude Code offers, the sandboxed shell it can run commands inside, and the classifier-backed mode built specifically to stop asking — each claim marked as either checked against this machine or taken from the documentation and not yet verified, so a later reader can tell which is which. Reporting it as a rate rather than a count matters, because the recorder also logs every command that ran, which is what makes a before-and-after comparison possible once a setting changes. The largest single category was multi-line blocks of Python or test code written straight into the shell — every one of which could have been written to a file and run plainly, with no interruption. Treat the shape of this as one day of one kind of work rather than a picture of normal use; the rate is the part worth comparing against later.

- (2026-08-03) Settled by measurement whether the rule files that are meant to load in every session actually come back after a long conversation gets summarized to free up room. They do.
