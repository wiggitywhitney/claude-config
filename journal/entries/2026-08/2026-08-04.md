### Summary
The developer documented a critical defect discovered during the sixth review round of the claude-config audit: two rule files (`rules/hooks-reference.md` and `rules/bats-bash-testing.md`) are configured to load through both mechanisms simultaneously — they carry `paths:` frontmatter *and* are `@`-referenced from the project's own `.claude/CLAUDE.md` file. This is the exact arrangement the project's rules explicitly forbid, since it loads the same content twice.

The core problem is that both tools built to catch this violation are blind to it. The checker (`check-rule-frontmatter.sh`) and the inventory script (`measure-context-load.sh`) both derive the set of `@`-referenced files by reading only `global/CLAUDE.md`, missing the references that live in the project's separate `CLAUDE.md`. The developer documented this as the third instance of a broader pattern the audit has been uncovering: checks passing confidently over real violations. In this case, the check cannot see the file where the violation lives. The developer recorded that teaching both tools to scan every `CLAUDE.md` is the correct fix (the "derive" remedy) and is the responsibility of the upcoming Milestone A4. The per-file remedy — whether to drop the `@`-reference or drop the `paths:` frontmatter — is deferred as a deliberate decision rather than a cleanup task.

Whether project-level imports are re-resolved after compaction, load only at session start, or fail to resolve entirely remains unsettled and requires another measurement run. ## 6:53:05 AM CDT - Commit: 06adb99

### Summary
The developer fixed two tests in the measure-context-load.bats suite that weren't actually asserting anything about the behavior they claimed to test. The suite had been retrofitted onto a working script rather than written test-first, so the developer checked whether each test would catch a regression by deliberately reintroducing the defects they're supposed to catch and confirming the tests turned red. Ten of twelve defects were caught immediately, but two tests stayed green even when the code was broken.

The code-span test had a fixture that wrote a file path inside backticks with no whitespace after it—`` `@~/.claude/rules/mentioned.md` ``—but the reference matcher requires whitespace, end-of-line, or a closing paren after the path. A backtick doesn't qualify, so the reference failed to match regardless of whether the code was stripping code spans or not. The test was passing for reasons unrelated to what it was testing. The developer fixed the fixture to include whitespace after the path, mirroring the actual case in the project's global/CLAUDE.md file.

The frontmatter-boundary test had the same problem. Its fixture used "This rule discusses paths: in prose" where `paths:` wasn't at the start of a line, so the pattern `^paths:` wouldn't match it no matter where the frontmatter boundary was drawn. The developer changed it to put `paths:` at column zero below the frontmatter block, which is the actual case that distinguishes correct parsing from a whole-file grep.

A third test initially failed the mutation check, but that turned out to be the mutation's fault rather than the test's—it had pointed a guard at a nonexistent path, making it fire unconditionally instead of removing the behavior. That case was recorded in the decision log since a broken mutation produces a false accusation against a sound test.

The developer also updated PROGRESS.md and the audit decision log to document the findings. The broader takeaway went into the decision log: "tests exist" and "tests would catch a regression" are different claims, and the project has been treating them as one. None of the other bats suites in the repo have been checked this way.
