## 3:45:39 AM CDT - Commit: b37c619

### Summary
The developer removed the YouTube MCP safety hook from the configuration and codebase, then brought a previously untracked rules file under version control and documented why two other safety hooks must stay as they are.

The YouTube hook had been blocking delete and upload operations on YouTube MCP tools, and testing confirmed it worked correctly—but the capability it guarded was unreachable. The configuration pointed to a wrapper script that didn't exist, so the YouTube MCP server never started in the first place. The only working YouTube integration offered transcript downloads, which the hook allowed anyway. The developer decided to remove it, reasoning that a guard for something absent should go away, and if the upload-capable server ever comes back, that's the right moment to add protection back deliberately. Two pieces of dead configuration fell out alongside it: the broken server entry in `~/.claude.json` that failed silently on every session start, and a stray copy of the Google CLI safety hook sitting in `~/.claude/scripts/` while the live version was tracked in the repository—the third instance this week of the same file living in two places.

The Google CLI safety hook stayed unchanged, but the developer documented exactly why its over-blocking behavior must not be "fixed." It matches command text rather than tool invocations, so echoing a blocked command gets denied, and so does a shell heredoc containing the command as test data. This blocked the initial test run and then blocked the attempt to document the behavior through a heredoc example. The hook is the only one in the set where a false negative sends an irreversible message to a real person, while a false positive just costs one retyped command—that asymmetry justifies the over-blocking and justifies the opposite decision for advisory notices. The developer recorded this explicitly so a future reconciliation for consistency wouldn't trade a cheap annoyance for an expensive failure.

The developer also brought `rules/decktape-gotchas.md` under version control and added it to the rules index. The file documented real surprises about converting slide decks to PDF—why appending a print parameter to the URL stalls the capture, why the tool needs a served address rather than a local file path, why the page size has to match what the deck was authored at, and why a native install beats the container image on this machine. It had been correctly scoped to only load when slide files were open, and it was candid about what it couldn't confirm. What it was missing was any existence outside one laptop: the tool that loads these rules read them from disk rather than from version control, so the guidance was live and firing while being one disk failure from gone, and absent from the index that makes rules discoverable.

The test suite stayed at 376 passing tests with 50 cluster tests passing.
