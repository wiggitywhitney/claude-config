## 6:37:42 AM CDT - Commit: 0a3faa6

### Summary
The setup script had been broken in two independent ways, both of which prevented machines from provisioning correctly. The developer fixed both issues and repaired a test suite that had been silently crashing.

The first problem was that `setup.sh` carried a hardcoded list of six skills to install while the repository actually holds twenty-four. This meant a freshly provisioned machine would come up missing every skill needed for the PRD and issue workflows—the ones used daily. The developer changed both the install and uninstall paths to derive their lists from the actual directory structure instead of maintaining a list that could drift out of sync. They verified the fix by confirming that reverting to the old hardcoded approach would fail the new tests and expose all eighteen missing skills.

The second problem was that `setup.sh` was exiting with an error on every run and installing nothing at all. The script validates that each hook path in the settings template actually exists, but the template still pointed at `scripts/google-mcp-safety-hook.py`—a YouTube MCP safety hook that had been deleted earlier in the same milestone. That single deletion ended up recorded in four different places: the live settings (cleaned when it was removed), the settings template (stale), a test fixture (stale), and a test assertion (stale). Only the live settings had been cleaned up. The fourth location—the test assertion—should have caught this immediately, but the test suite was crashing earlier in its run, so it never got that far.

The crash itself turned out to be the most important finding. The test suite was aborting at test three of one hundred fifty-six with an uncaught error, which meant the run produced no failure lines at all. The CI comparison table was recording this as zero failures, which looked like reassurance for twelve days—but zero failures and "the suite never got past test three" are the same reading unless you check whether a total was printed. The developer annotated the table to flag this.

The developer also replaced a hardcoded expected hook-path count with one derived from the settings template, since a literal number there breaks every time a hook is added or removed and makes failures look like "someone changed the hooks" rather than "a hook path is broken." They added tests asserting that every skill and command in the repository gets provisioned, and they caught a subtle issue where two new test functions had been appended after the `if __name__ == "__main__"` block, which meant they were never actually called—they existed, were correct, and did nothing. The tests moved above the block and now run.

After these changes, the test suite went from aborting after two tests to running all one hundred fifty-six tests, all passing. Across the full test suite, there are now one thousand passing tests and fourteen failing (the same pre-existing failures that were there before).
