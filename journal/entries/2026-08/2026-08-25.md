### Summary
The developer fixed a broken shell command for loading secrets that had been wrong in every copy since February. The command named a flag the secrets tool doesn't accept—`vals eval --output shell` fails immediately with "flag provided but not defined: -output"—so the export never ran and every variable it was supposed to set was silently missing. This is why a background service needing an API key wouldn't start.

The developer corrected the command across three files (`.claude/CLAUDE.md`, `guides/vals-usage.md`, and `rules/vals-secrets.md`) to use the working form: `eval "$(vals env -export -f .vals.yaml)"`. They verified this against vals 0.43.6, confirming the broken version reproduces the flag error and the new one exits cleanly, emitting one export line per secret.

What makes this worth more than a quick three-line fix is how the mistake survived six months. The wrong command arrived in the February bootstrap, got copied into a second file a week later, and then in March the one file that had it right was deliberately edited to match the two wrong copies—the reasoning was to make the project internally consistent, without anyone actually running any of them. The developer added detailed notes to all three locations explaining what was verified and on which version, and explicitly warned against aligning them back to the broken form. They also noted that whether `--output shell` ever existed in any older vals release is unchecked, and that consistency with an unverified copy is what destroyed the last working one in the first place.
