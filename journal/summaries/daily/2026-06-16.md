# Daily Summary — 2026-06-16

## Narrative

The developer spent the day implementing a complete GitHub issue workflow skill suite—six tools that mirror the existing PRD workflow skills but work with GitHub issues instead. The work started with detailed planning and ended with all skills built, tested, and globally available.

The day opened with creating a detailed PRD that outlined the entire suite. The developer designed the workflow to handle issue-based work the same way PRD work is handled: starting work with `/issue-start` (which recommends issue pairings and creates named branches), checkpointing progress with `/issue-update-progress`, picking up where they left off with `/issue-next`, cascading decisions across related work with `/issue-update-decisions`, and closing issues with `/issue-done`. A sixth skill, `/issue-create`, guides the full issue creation process. The developer made several key design calls during planning: branch names needed both issue numbers and semantic descriptions so downstream skills could know which issues to close; progress should live in GitHub issue comments plus git commits rather than body edits to avoid notification spam; and the `/issue-update-decisions` skill needed to cascade across all open issues and PRDs, not just the current working set, to keep related work consistent.

A crucial methodological decision emerged early: instead of writing new skills from scratch, the developer decided to duplicate each corresponding PRD skill's documentation verbatim and then edit minimally. The PRD skills are battle-tested and handle edge cases correctly, so copying them preserves working patterns and prevents silent gaps. Only change what must change. This approach was reinforced across the day as the developer built each skill—reading the PRD counterpart top-to-bottom, copying it as-is, identifying what must differ for issues, and making only those targeted edits.

The developer then worked through the implementation sequentially. `/issue-create` was built first, guiding users through drafting a well-formed issue body with problem statement, solution, and acceptance criteria, then running a review step before creating the issue. The skill also handles ROADMAP.md updates conditionally since not all repos have that file. `/issue-start` came next, analyzing open issues to surface juggling candidates, waiting for the user's decision on which issues to work together, then creating a branch that encodes all issue numbers in its name. `/issue-update-progress` synthesizes what got done and what comes next from conversation context and git history, proposes a structured checkpoint comment for confirmation, and posts it to the relevant issue—mirroring the auto-synthesis behavior of the PRD equivalent rather than asking the user to fill in a form. `/issue-next` reconstructs working context at the start of a fresh session by reading the most recent checkpoint comment and supplementing it with recent git log. `/issue-update-decisions` records design decisions in an issue's Decision Log and cascades their impact across all open issues and PRDs, using safe temp-file edits for multi-line updates. `/issue-done` closes out work end-to-end: ensuring a PR exists, running the CodeRabbit review gate, updating PROGRESS.md and ROADMAP.md, merging the PR, closing all issues in the working set, and cleaning up branches.

Throughout implementation, the developer caught and fixed several details. The PROGRESS.md checkbox in `/issue-create` was moved into its own section to ensure it never got skipped. Priority information was added to the gather flow so issues could be placed correctly in ROADMAP. M6 workflow steps were reordered so changelog updates happen before merge rather than after, keeping them part of the merged PR. The developer also added a requirement that each skill implementation audit both global and project-level CLAUDE.md files for issue-specific procedures that should be integrated into the skills.

Late in the day, the developer noticed the PRD skill `/prd-done` had a gap: it was missing a re-review step after addressing CodeRabbit feedback and wasn't checking all three places where CodeRabbit posts findings (pull request reviews, inline comments, and issue comments). The developer fixed both issues by adding a three-channel fetch strategy and a re-review loop that repeats until no new Fix-level findings remain.

The suite was completed by installing global symlinks for all six skills in `~/.claude/skills/`, making them available across any repository. The developer verified they worked by testing in another repo. They also opened a follow-up issue to apply the same symlink pattern to the PRD skill suite, which currently lacks global availability.

By day's end, the PRD was marked complete and archived. All seven milestones—six skill implementations plus global symlink installation—were finished.

## Key Decisions

- **Duplicate PRD skill SKILL.md files verbatim as the starting point for issue skills, then edit minimally** — Battle-tested PRD skills already handle edge cases and wording correctly. Copying preserves working patterns and prevents drift from proven implementations. Only change what must change to adapt for issues. Tradeoff: requires careful review of each section before deletion to ensure no issue-equivalent exists.

- **Verify before removing any section from a duplicated PRD skill — when in doubt, ask** — Sections that appear PRD-specific may still have issue equivalents (e.g., ROADMAP.md updates apply to both). Silent deletions introduce gaps that are hard to detect. Example: ROADMAP.md logic should be kept conditional, not deleted, because some repos track both PRDs and issues in the same ROADMAP.

- **Progress for issues stored in GitHub issue comments plus git commits** — Issue body is the problem statement; appending work logs clutters it. GitHub issue body edits fire notifications on every edit; comments are append-only and less noisy. Comments survive machine loss and are accessible without the local repo. Git commits capture code changes; checkpoint comments capture work state. Tradeoff: requires structured checkpoint comment format that must be parsed by `/issue-next`.

- **Checkpoint comment posted to the relevant issue only, not all issues in juggling set** — When working set contains multiple issues, explicitly ask user which issue is most relevant before posting.

- **Branch naming includes both issue numbers and semantic description** — Issue numbers provide machine-readable identification for `/issue-done` to know which issues to close. Semantic description provides human readability. Format: `feature/<issue-numbers>-<semantic-description>`.

- **`/issue-start` recommends juggling pairs before creating branch** — Branch name encodes issue numbers, so working set must be decided before branch creation. Two-phase flow: analyze and recommend juggling candidates, user decides, then create branch.

- **`/issue-update-decisions` cascades to all open issues and PRDs** — Same scope as `/prd-update-decisions`. Design decisions affecting one issue often affect other in-flight work regardless of juggling set membership. Narrower scope would leave related work inconsistent.

- **Issue skills globally available via symlinks from `~/.claude/skills/`** — Issue skills are used across all repos, not only in claude-config. Follows established pattern for globally available skills. Makes skills immediately usable in any project without per-repo setup.

- **Audit CLAUDE.md files before writing each skill** — Each skill implementation must check both global (`~/.claude/CLAUDE.md`) and project-level (`.claude/CLAUDE.md`) configuration files for issue-specific procedures that should be integrated into the skill.

- **Synthesize progress from conversation context and git log instead of asking user to fill in progress manually** — Mirrors the proven pattern from `prd-update-progress` which auto-derives progress rather than requesting manual input. Reduces friction by proposing complete checkpoint comment for user confirmation or editing.

- **Minimal-diff approach to writing issue skills from PRD counterparts** — Issue skills are written by copying the corresponding PRD skill verbatim, then making only targeted edits needed for issue context. Preserves battle-tested patterns, wording, and edge-case handling. Prevents regressions and drift from rewriting sections that work identically for both contexts.

- **Clarify Step 0 framing across milestones to lead with battle-tested-copy rationale** — Updated milestone step descriptions to explicitly state "The PRD skill is the battle-tested reference. Your job is identifying the minimal diff..." Ensures implementers understand the approach before starting.

- **Auto-synthesize progress from conversation context first, then git log as fallback** — Conversation context is primary source for what got done and what comes next. Falls back to `git log --oneline -10` if conversation is insufficient. Proposes complete checkpoint comment body to user for confirmation before posting.

- **Checkpoint comment format is the parsing contract for `/issue-next`** — Format documented verbatim with exact sentinel string `## Progress Checkpoint` at start of comment body. Fields: Branch, Done, Next step, Open questions (optional).

- **Extract issue numbers from branch name and validate format in `/issue-done`** — Branch names follow `feature/<numbers>-<description>` format from `/issue-start`. All issue numbers in the working set appear in the branch name. Non-standard branch names require explicit user input before proceeding.

- **Require CodeRabbit review gate before merge** — Full CodeRabbit + `/code-review` gate must pass before proceeding to merge. Fetch findings from all three GitHub API channels. Present all findings to user. Triage per workflow rules. Re-review after pushing fixes until no new blocking findings remain. Explicit human approval required before merge.

- **Update PROGRESS.md with changelog entry during close-out** — Add entry under `## [Unreleased]` with format: `- (YYYY-MM-DD) [What changed and why, including reasoning]`. Commit PROGRESS.md on feature branch before merging so entry is part of merged PR.

- **Remove completed issues from ROADMAP.md** — Check for `docs/ROADMAP.md` presence. Remove entries for closed issues from ROADMAP. ROADMAP is forward-looking; completed work belongs in PROGRESS.md only. Commit alongside PROGRESS.md if changes made.

- **Resolve OWNER/REPO via gh repo view command** — Use `gh repo view --json owner,name` to dynamically resolve OWNER and REPO values. Eliminates placeholder ambiguity in CodeRabbit API fetch commands.

- **Add three-channel CodeRabbit API fetch strategy to prd-done review workflow** — CodeRabbit posts findings across three separate endpoints: `/pulls/{n}/reviews`, `/pulls/{n}/comments`, and `/issues/{n}/comments`. Missing any one means missing findings. Previous workflow only checked one endpoint.

- **Add re-review loop after addressing CodeRabbit feedback** — After pushing fixes to address feedback, start a 7-minute timer and re-run all three API calls to verify no new Fix-level findings remain. Provides mechanism to handle rate-limiting by posting `@coderabbitai review` comment to trigger re-review.
