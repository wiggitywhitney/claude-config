# Daily Summary — 2026-08-04

## Narrative

The developer spent the day working through the sixth review round of a Claude Code configuration audit, uncovering systemic problems with the checking tools themselves and then carefully fixing them.

The day started with discovery. A hung CodeRabbit review had left five findings, two of which were real. One finding exposed a critical blind spot: two rule files were configured to load through both mechanisms simultaneously—they carried `paths:` frontmatter *and* were `@`-referenced from the project's own `.claude/CLAUDE.md` file. The project's rules explicitly forbid this arrangement since it loads the same content twice. The real problem was that both tools built to catch this violation couldn't see it. The checker and the inventory script both derived their set of `@`-referenced files by reading only the global `CLAUDE.md`, missing the references that lived in the project's separate config file. The defect exposed approximately 10,937 bytes classified incorrectly—about 17% higher than the recorded total—and in the unsafe direction for the byte budget.

Rather than just fix those two files, the developer fixed the tools themselves. Both `check-rule-frontmatter.sh` and `measure-context-load.sh` now scan every `CLAUDE.md` file in the project, and the checker reports which file carries each reference so the fix is unambiguous. When the tools started looking at both files, they immediately surfaced the two real violations. Since the global config already documented both files as "reference pointers, not auto-loaded," the project config was contradicting a decision already recorded. The stray `@`-references were removed to match the global file's intent.

The developer then discovered the always-loaded total was wrong. It had been reported as 63,619 bytes, but the project's own `.claude/CLAUDE.md` file was never being tallied even though it loads in every session just like the global one does. Adding that and fixing the misfiled rules brought the correct total to 70,228 bytes. The developer also expanded test coverage from 19 to 23 tests in the frontmatter checker and 29 to 33 in the load-inventory script, all written to fail first. When mutation testing was applied to confirm the tests would actually catch regressions, two tests turned out to be passing for reasons unrelated to what they claimed to test. The fixtures were rewritten to match the actual cases the tests were supposed to catch.

With the measurement tools now producing accurate counts, the developer turned to the permissions research that had been running in parallel. The original plan was to mine 939 transcripts for permission data, but that turned out to be impossible—approved prompts look identical to ungated calls in the saved transcripts, and rejected ones carry no reason. Instead, the developer found two undocumented notification hooks in the shipped binary (`PermissionRequest` and `PermissionDenied`) that actually carry the data needed. A live logging instrument was installed using these hooks, verified working in real time.

The core permissions question shifted during this work. The narrow question was "why does it interrupt Whitney," but the real question was broader: how do other practitioners run Claude Code unattended for hours without constant approval prompts? The developer split the work into two pieces—a short relief pass now that reads the official documentation on permission modes and sandbox settings, and the durable research staying with the later documentation milestone. The narrow question itself was added to the community-practices sweep that happens in parallel.

The developer then measured the actual interrupt rate: 16 interruptions across 182 tool calls over roughly 7.5 hours, which works out to 8.8%. But when the measurement was done properly with a committed script instead of by eye, something unexpected emerged. The looser permission mode (`acceptEdits`) showed a *higher* prompt rate than the strict one (`default`), not a lower one. This directly contradicted the obvious fix—"just use a looser mode"—and meant the remedy had to change the approval *mechanism*, not loosen the existing one.

The developer researched the platform's official documentation on permission modes, sandbox, and auto-accept, verified each claim against the live setup rather than trusting the page, and found that auto mode was exactly what the platform offered for this problem. The documentation section is titled "Eliminate permission prompts with auto mode," and the mechanism replaces string-matching a command against an allowlist with a classifier that judges what the command does. This explained why 227 allowlist entries had prevented none of the observed interruptions—an allowlist entry approves a literal command string and generalizes to nothing. The developer adopted auto mode provisionally by adding it to the settings file, verified every prerequisite, and wrote a 210-line research document that documents the six permission modes, the sandboxed Bash tool, and auto mode, with every claim marked either verified-against-this-setup or documentation-only.

At that point, the developer made a strategic decision to drop the expensive second half of the permissions milestone. The plan had been to extract a binary trigger-class inventory from transcripts and rank it by observed frequency, separating settings-fixable classes from behavior-only ones. But auto mode bypasses the command-shape classes wholesale instead of fixing them one at a time, which made the census into an inventory of prompts Whitney no longer receives. The most valuable finding came from about twenty minutes of reading official documentation, not from the instrument that was built to find it. The developer noted this as a lesson for future work: before building any measurement rig, check whether the platform already answers the question.

Throughout the day, the developer also fixed several documentation contradictions that had accumulated. A byte budget table had omitted the project configuration file while counting its bytes. Milestone A1 was marked complete while still directing readers to run a screening pass that had already executed. Milestone B4 still carried decision-making duties that had been reassigned elsewhere. A commit-message hook was documented to clarify its matching behavior. Two shell scripting gotchas were promoted from comments into the rules. Testing guidance was updated to capture a mutation-testing lesson. A baseline of fourteen pre-existing test failures was established so later work wouldn't be blamed for them.

By day's end, the developer had moved from discovering that checking tools were blind to real violations, to fixing the tools themselves, to using the corrected measurements to drive a completely different solution path for the permissions problem. The work involved reconciling contradictions between documentation and measurements, correcting test discipline, and generalizing a pattern that had repeated three times across the project: agreed rules lost to habit. Rather than documenting the same guidance a fourth time, the developer recorded this as an open question for later: what makes a rule actually stick—documentation enforcement or mechanical enforcement like hooks?

## Key Decisions

- **Scan every CLAUDE.md for imports, fixing the tools that couldn't see violations**: Both the rule-frontmatter checker and the load-inventory script now read both the global and project configuration files instead of just the global one. This immediately surfaced two real both-mechanisms violations that had been invisible to the old tools.

- **Correct the always-loaded total to 70,228 bytes**: The project's own `.claude/CLAUDE.md` file was never being tallied despite loading in every session. Adding it plus fixing misfiled rules brought the correct total from 63,619 to 70,228 bytes.

- **Split imported-rule byte counts by configuration file source**: Imported rules are now tracked per source so a single project-level import won't be misread as growth in the global set, preventing silent redefinition of historical comparisons.

- **Recognize all three import spelling forms in the rule-frontmatter checker**: The inventory script had always matched `@rules/`, `@./rules/`, and `@~/.claude/rules/`, but the checker recognized only one form, causing the two tools to disagree about the same files.

- **Report compaction survival verdict based on import source for dual-mechanism rules**: Only user-level imports were observed re-resolving after compaction; project-level re-resolution is unmeasured. A both-mechanisms rule imported only from the project file reports `untested` rather than inferring a verdict.

- **Approved permission prompts leave no persistent record, invalidating the transcript-mining premise**: Approved prompts look identical to ungated calls in saved transcripts. Instead, two undocumented hook events (`PermissionRequest` and `PermissionDenied`) in the shipped binary carry the data needed.

- **Split Milestone A3 into a narrow relief pass now and durable research later**: The narrow pass reads official Claude Code documentation on permission modes and sandbox settings, proposes one provisional change measured with a live instrument. Full capability research stays in a later milestone to avoid currency problems.

- **Adopt auto mode provisionally via permissions.defaultMode**: The platform's own answer to the approval-friction question. It replaces string-matching commands against an allowlist with a classifier that judges what the command does. This is reversible; permanent settings decision stays with later review.

- **Mode strictness does not explain observed interruption rate**: Measured with a committed script: the looser `acceptEdits` mode showed 9.3% prompt rate versus the stricter `default`/`Manual` at 6.1%. Looser mode had a higher rate, contradicting "just use a looser mode" as remedy.

- **Settings-fixable residue is exactly two ask rules**: `Bash(rm *)` and `Bash(git merge*)` are explicit ask rules that force a prompt in every mode including auto. These two rules account for 1 of the 21 baseline prompts after classifier fixes.

- **Drop Milestone A3 half two (trigger-class census) rather than defer**: Auto mode bypasses command-shape classes wholesale instead of fixing individually. The census would become an inventory of prompts no longer being received. The expensive half is dropped against stated cost constraints.

- **Check whether platform already answers question before building measurement instrument**: The most valuable finding in Milestone A3 came from twenty minutes reading official documentation, not from the instrument. This principle applies to future milestones.

- **Measure approval-prompt rate with committed script rather than by eye**: Decision 25 forbids reading rates off logs by eye. The script splits by mode and command shape and includes regression tests for two measurement mistakes made and corrected.

- **Separate the configuration-and-rules subtotal from the total including skill descriptions**: Skill descriptions load into the startup listing and belong in any real byte budget, but the subtotal must preserve the meaning that earlier measurements refer to. Silently redefining it would break historical comparisons.

- **Guard grep against no-match status under pipefail**: `grep -q` returns 1 on no match, which propagates as pipeline failure under `set -o pipefail`. This is a latent defect that becomes real once `set -e` is added.

- **Anchor the prompt classifier to the invoked command**: The trigger classifier was matching rule names anywhere in the command text, so `echo rm $TMPDIR` counted as an ask-rule prompt even though `rm` wasn't being invoked. Both patterns are now anchored to command start or positions after shell operators.

- **Generalize the "agreed discipline lost to habit" pattern into one enforcement question**: Three instances share the same shape: command-shape discipline, the approval-prompt instruction, and TDD ordering. All three were written down, agreed to, and then lost to habit. The pattern points to a general problem about how agreed disciplines are actually enforced. Deferred to later review with practitioners' answers as input.

## Open Threads

Three possibilities remain open: project-level imports not re-resolved after compaction, load only at session_start with probe installed too late, or fail to resolve at all.

Repo-root or nested CLAUDE.md files picked up by directory traversal remain unscanned. This is a latent gap rather than a live undercount since neither location is in use in this repository.

The in-repo comparison shows ABOUTME headers are hook-enforced and hold firm while TDD and approval-prompt rules, which are documentation-enforced, did not. The question of what makes a rule actually stick is deferred to later review.

- **Auto mode's classifier is judgment not guarantee**: The adoption is provisional. The classifier pauses after three consecutive or twenty total blocks, and two existing allow rules go dormant in auto mode while it's active, converting instant approvals into classifier round-trips.

- **The instrument for measuring permission events survives in gitignored files**: The live logging instrument was installed in `.claude/settings.local.json` logging to `~/.claude-a3-scratch/permission-events.jsonl`. It stays installed by agreement so an after-window can accrue at no cost. Teardown and after-measurement carry to the final milestone.
