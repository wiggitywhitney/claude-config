# Daily Summary — 2026-08-25

## Narrative

The developer spent the day fixing broken documentation and correcting false claims scattered across the repository—work that surfaced a pattern of how mistakes propagate and survive when consistency is enforced without verification.

The morning started with a critical fix: a shell command for loading secrets had been wrong in every copy since February. The command used a flag (`--output shell`) that the vals tool doesn't accept, causing the export to silently fail and leave every secret variable missing. This is why a background service needing an API key wouldn't start. The developer traced how the mistake survived six months: it arrived in the February bootstrap, got copied into a second file a week later, and then in March the one file that had it right was deliberately edited to match the two wrong copies—the reasoning was to make the project internally consistent, without anyone actually running any of them. They fixed it across three files and added detailed notes explaining what was verified and on which version, with an explicit warning against aligning back to the broken form. They also noted that whether `--output shell` ever existed in older vals releases is unchecked, and that consistency with an unverified copy is what destroyed the last working one in the first place.

Later that morning, the developer scored a code reviewer sub-agent against three real defects from the project's recent history to see how well it catches problems before they reach production. The reviewer caught 2 of 3: it identified two claim-versus-evidence defects where contradicting proof existed elsewhere in the repository, but missed a logic error in a shell loop—one it actually read and incorrectly cleared as sound. The distinction matters more than the fraction. Both catches involved assertions contradicted by written evidence or tool output the reviewer could access. The miss required reasoning about what code does rather than comparing two texts side-by-side, revealing a pattern: this reviewer is a strong checker of assertions and an unproven checker of code. The trial also exposed two operational problems. The `maxTurns` cap truncates reviews silently—two first attempts stopped at exactly 30 tool uses and returned only opening sentences with no indication they were incomplete. Token costs turned out to be measurable after all: each run reported its own usage at roughly 80,000 to 105,000 tokens per review, with truncated runs costing as much as successful ones. The developer also corrected a capability table that had recorded stall detection as nonexistent when the harness actually does detect it.

In the afternoon, the developer corrected documentation that made false promises about how the project's PRD completion workflow operates. The skill description claimed it would invoke automatically once all items were checked off, but nothing in the system actually triggered it that way. Rather than implement automatic invocation, the developer removed the claim. The reason is sound: the final step that skill takes is a merge, and the project requires human review before merging, so keeping this as a manual hand-off is the correct design. The same false claim appeared in a second file summarizing the first, and both were updated. The developer documented the reasoning directly in the text to prevent someone from "fixing" it back for consistency later—a safeguard against a pattern that had already broken a working command earlier that week.

The developer then removed two outdated references to a safety hook that had been deleted a week prior. The first was a line in the README listing the hook in the repository layout; the second was an entry in the hooks reference documentation claiming that destructive YouTube operations were being blocked by this hook. Since the hook no longer existed and no configuration file registered it, the documentation was asserting a protection that wasn't actually in place—a condition more dangerous than having no documentation at all, because a session reading it could reasonably attempt a destructive operation under the false belief that something would prevent it.

Near the end of the day, the developer documented a known limitation in the autonomous mode skill where the first of its two intended functions has never worked in practice. The skill installs symlinks to more permissive skill variants and loosens permissions, but personal skills take precedence over project ones, so the installed variants are shadowed and never load. This finding had been recorded in a research document weeks earlier, but nothing in the skill itself explained the partial failure, leaving users with the impression that the full feature was active when only the permission-loosening half was actually running. The developer added a clear explanation stating that step one does not take effect while step two does, and emphasized why this particular direction of failure is problematic—the guardrails come off while the autonomous hand-offs they were meant to serve remain inactive. They also verified two related `INVOKE AUTOMATICALLY` claims and confirmed they were accurate, deciding to leave those descriptions unchanged since they document what the variants actually instruct even though those files are not being loaded.

Finally, the developer updated the documentation file recording Claude's code sub-agent capabilities to correct three findings that a trial run had disproved. They revised claims about stall detection, idle-worker timeouts, and per-run cost measurement to reflect what the trial actually observed rather than what the official documentation implied. The header was restructured to distinguish between documentation-derived claims and observations from the trial, establishing that observed behavior takes precedence where they conflict.

## Key Decisions

- **Repair the vals shell-export command across three documentation files** — The documented command `vals eval -f .vals.yaml --output shell` fails immediately because vals eval has no `--output` flag. The correct command uses `vals env -export -f .vals.yaml`. Verified against vals 0.43.6. Added explicit notes to all three files stating not to re-align back to the broken form and documented that whether `--output shell` existed in older vals releases is unchecked.

- **Remove false promise that the PRD completion skill self-invokes** — The skill description claimed automatic invocation once all items were checked off, but nothing in the system actually triggered it. Removed the claim rather than implementing automatic invocation because the final step requires human review of CodeRabbit feedback before merging, so manual hand-off is the correct design.

- **Document that the autonomous mode skill's primary mechanism does not take effect** — Personal skills take precedence over project skills, so symlinks to YOLO variants installed by the skill are shadowed and never load. The skill's documentation now explicitly states that step 1 (installing YOLO variants) does not take effect while step 2 (loosening permissions) does. The dangerous direction of this partial failure is emphasized: guardrails are removed while the autonomous hand-offs those permissions were meant to serve remain inactive.
