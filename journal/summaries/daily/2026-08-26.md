# Daily Summary — 2026-08-26

## Narrative

The developer spent the day reworking how progress gets recorded and pushed to the repository. It started with a discovery: the branch had accumulated 104 commits ahead of main, with 44 of those never pushed to the remote. Digging into why revealed the real problem — the progress-recording skill explicitly instructed against pushing, framing commits as safe local checkpoints. That sounded reassuring but wasn't. Work stuck on a single laptop is one disk failure away from disappearing, and the repository had quietly built up nineteen days of unpushed commits, including twenty-two journal files the project's rules mark as unrecoverable. Nobody noticed because nothing made that gap visible.

The developer rewrote the progress-recording skill to make pushing a normal part of the workflow instead of something to actively avoid. The key insight was timing: push after CodeRabbit runs its review, not before. This lets findings get triaged immediately while the work is still local — problems can be fixed right away rather than discovered later when pushing becomes harder. The push doesn't wait for a clean report; it waits for findings to be triaged (fixed, deferred to an issue, or skipped with a reason), since the review rules allow deliberately skipping findings. The developer also added explicit guidance for what to do when a push gets refused by pre-push hooks or review gates — do what the refusal asks and try again, never bypass the checks with flags like `--no-verify`, because those checks are the only thing preventing secrets or unreviewed code from reaching the remote.

Shortly after, the developer deleted the push gate mechanism that had been built the day before. The gate was meant to block pushes until a diff review had been recorded, but after trying it on a real push, it became clear the whole apparatus was unneeded complexity. CodeRabbit was already wired in and running as a different-vendor checker — that was the whole point of copying the idea in the first place, and building a same-vendor gate lost that property. CodeRabbit handled 15,000+ line diffs without dropping files; the new gate truncated at around 1,000 lines. It also found both of the gate's own bypasses, caught overstated claims about what the reviewer prevented, and only ever checked that a note existed rather than that an actual review happened. Most damaging, with push now a step in the progress-update workflow, the gate converted every progress update into a stop — friction pointing the wrong way. The developer kept the reviewer and the `/diff-review` command but rewrote it as something you invoke deliberately rather than something that blocks a push. All the trial measurements stayed in the codebase — the per-run cost figures, the truncation behavior, the stall-watchdog correction — because those are what the design milestone actually needed.

## Key Decisions

- **Reposition push operation to occur after CodeRabbit review instead of before** — Timing lets findings get triaged while work is still local, so problems can be fixed immediately rather than discovered later.

- **Make pushing a standard part of progress recording workflow rather than optional** — Work trapped on a single laptop is one disk failure away from disappearing; the repository had accumulated nineteen days of unpushed commits without anyone noticing.

- **Change push readiness condition from "clean review" to "triaged findings"** — The review rules allow deliberately skipping findings, so waiting for zero findings would mean never pushing at all.

- **Add explicit handling for push refusal scenarios** — When pre-push hooks or review gates deny a push, follow what the refusal asks and try again; never bypass the checks with flags like `--no-verify`, since those checks are the only thing preventing secrets or unreviewed code from reaching the remote.

- **Remove the push gate and keep the reviewer as a manual command** — CodeRabbit (different-vendor) was already wired in and handled larger diffs better; same-vendor lost the property that made the idea worth copying. The gate only checked that notes existed rather than that actual review happened, and with push now in the progress workflow, it converted every progress update into a stop. The `/diff-review` command was rewritten to dispatch and report without gating on the result.
