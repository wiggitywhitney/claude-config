Late in the day, the developer documented a discovery about globally-installed skills: nearly all 24 of 26 personally-installed skills are symlinks into the working tree rather than fixed revisions, which means branch state silently determines what skills load in every session across every repository. They showed this through a concrete example where a skill measured different token counts on different branches, and a compaction-cap defect that had been fixed on the feature branch silently reappeared when main was checked out. This finding extends an earlier precedence rule and raises a design question about whether working-tree symlinks should remain or whether skills should be copied on install or symlinked to a stable worktree.

## Key Decisions

- **Journal file merge policy**: Primary journal entries are unioned because either side may contain unique records; derived summaries take the fuller version since they can be regenerated. (Prompted by a specific merge where one entry had three commits on one side and two entirely different ones on the other.)

- **Symlinks for installed skills**: The codebase currently uses symlinks into the working tree, which means branch state silently determines what skills load. An open design question remains about whether to keep this behavior or decouple installed skills from branch state by copying on install or symlinking to a stable worktree.
