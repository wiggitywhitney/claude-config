# Daily Summary — 2026-09-11

## Narrative

The developer spent the day working through documentation and validation tasks across several interconnected areas.

They started early by adding a third test case to the pair-detection benchmark, documenting a tricky edge case: two byte-identical PR template files that differ only by filename case and sit in the same directory. This pair escapes both existing detection classes—one by design (it only looks across directories) and the other because it would need to scan within directories rather than across them. The developer flagged this as a hard requirement: any detection class that can't find two identical files next to each other isn't ready for use.

Mid-morning, they updated the PRD #109 document to fold findings from a pull request review into the project plan. This involved reclassifying test failures, correcting stale claims that span multiple locations, and flagging internal contradictions within PRD #84 itself.

Around midday, the developer caught and fixed a false positive in the review-coverage verification rule. GitHub re-anchors inline comments to the newest commit whenever their surrounding code stays unchanged, which meant an inline comment's commit ID could point to a newer commit than the review that actually created it. This caused a review of an older commit to appear as if it covered the current head. The fix narrowed the acceptance criteria to check only the reviews channel, which records what was genuinely reviewed and doesn't move.

Later that afternoon and evening, the developer expanded the scope of their findings. They documented that the rules directory, like the skills directory before it, is a symlink into the repository's working tree—meaning every always-loaded rule follows whatever branch is checked out. The review-coverage correction exists only on the current branch and vanishes when main is checked out. This widened the branch-dependence problem from skills alone to all instructions the repository supplies.

Finally, the developer surfaced and documented two distinct stop states in CodeRabbit's review service that had been conflated in the workflow rules. Both "review paused" and rate-limit notices hide inside HTML comments in the PR comment body, making them invisible in the GitHub web interface. A genuine pause could be mistaken for a clean review if someone grepped the raw text without handling HTML tags properly. The developer clarified that a rate limit means the service refused the work, while an auto-pause means CodeRabbit throttled because too many commits arrived during the review window—a self-inflicted condition from pushing repeatedly. Both require manual intervention, but the remedy differs. The rules now emphasize that you must grep the raw comment body without stripping HTML tags to catch these states, and that any manual trigger should be sequenced last, after all work is pushed and batched.

## Key Decisions

- **HTML comments hide CodeRabbit's stop states from standard grep operations** — Both "review paused" and rate-limit notices are wrapped as HTML comments in PR comment bodies and don't render in the GitHub web interface. Stripping HTML tags before grepping removes these markers entirely. The raw body text must be grepped without sanitization to detect these states.

- **Distinguish CodeRabbit's auto-pause from rate-limit states** — A rate limit means the service refused the work, while an auto-pause means CodeRabbit deliberately throttled because the branch received an influx of new commits during the review window. Auto-pause is self-inflicted by pushing during a review window. Both require manual intervention, but the fix for auto-pause is to stop pushing and batch the work. Manual triggers should be sequenced last, after all work is pushed, or they're wasted on a commit about to be superseded.

- **Review-coverage verification should check only the reviews channel, not inline comments** — GitHub re-anchors inline comments to the newest commit whenever their surrounding code remains unchanged, causing inline commit IDs to track the head rather than what was actually reviewed. This created false positives where an in-flight review appeared complete. The reviews channel records the commit that was genuinely reviewed and doesn't move.

## Open Threads

- **Whether branch-state symlink behavior should persist or be decoupled** — Nearly all personally-installed skills and rules are symlinks into the working tree, meaning branch state silently determines what loads across every repository. This creates problems: skills measuring different token counts on different branches, bugs silently reappearing when switching branches. The developer noted this as an open design question about whether this behavior should continue or be addressed through copying or stable worktree symlinks.
