# Daily Summary — 2026-09-11

## Narrative

The developer spent the day working through documentation and verification logic across several interconnected areas.

Early on, they added a test case to the pair-detection benchmark documenting a tricky edge case: two byte-identical PR template files that differ only by filename case and sit in the same directory. Neither of the existing detection classes would catch this pair—one by design (it only looks across directories), the other because it scans between directories rather than within them. They also noted this pair vanishes entirely on case-insensitive filesystems despite being tracked separately by git. This became a hard requirement: any detection class that can't find two identical files next to each other isn't ready.

Later, they pulled findings from a PR review into the PRD #109 document, folding in four concrete discoveries: a stale-claim correction spanning four locations, a reclassification of six test failures whose cause remains unknown, and a contradiction within PRD #84 where its own text still instructs a rejected plan. They also clarified that two files contradict themselves internally, requiring a full grep of each rather than fixing only the cited line.

In the middle of the day, they corrected the review-coverage verification rule after spotting a false positive during live code review. GitHub re-anchors inline comments to the newest commit whenever their surrounding code stays the same, so an inline comment's commit ID can point to a newer commit than the review that actually produced it. This made an old review appear to cover the current head because eleven inline comments had drifted forward while the review body stayed pinned. The fix narrowed the acceptance criteria to check only the reviews channel, which records the commit actually reviewed and doesn't move. Inline comments are no longer accepted as evidence.

They then widened the scope of an earlier finding: the rules directory, like the skills directory, is a symlink into the repository's working tree. This means every always-loaded rule follows whatever branch is currently checked out. The review-coverage correction they'd just made exists only on the current branch and vanishes when main is checked out, along with the incorrect guidance it replaced. This expanded the branch-dependence problem from skills alone to all instructions the repository supplies.

Late in the day, they documented two distinct stop states in CodeRabbit's review service that had been conflated in the workflow rules. Both "review paused" and rate-limit notices are wrapped in HTML comments in the PR comment body, making them invisible in the web interface and easy to miss without proper handling. A genuine pause could be mistaken for a clean review. The fix separates them: a rate limit means the service refused the work outright, while an auto-pause means CodeRabbit throttled because too many commits arrived during the review window—a self-inflicted condition from pushing repeatedly rather than batching. Both require manual intervention, but the remedy differs. The rules now clarify that you must grep the raw comment body without stripping HTML tags to catch these states, and that any manual trigger should come last, after all work is pushed and batched, to avoid wasting it on a commit about to be superseded. This discovery came from a conversation where the developer realized they'd nearly dismissed a real pause by sanitizing input before checking it, and recognized they'd caused the situation themselves by pushing five times during the review window.

## Key Decisions

- **Narrow review-coverage verification to the reviews channel only** — GitHub re-anchors inline comments to the newest commit when their diff hunks still apply, causing inline commit IDs to track the current head regardless of what was actually reviewed. This creates a false-positive window where an in-flight review appears complete. The reviews channel is stable and reflects what was genuinely reviewed.

- **Detect CodeRabbit's stop states by grepping raw comment body without HTML tag stripping** — Both "review paused" and rate-limit notices hide inside HTML comments in PR comment bodies. Stripping tags before grepping removes these markers entirely. Raw body text must be searched without sanitization.

- **Distinguish CodeRabbit's auto-pause from rate-limit states** — Rate limit means the service refused the work; auto-pause means CodeRabbit throttled due to commit influx (self-inflicted by pushing during review). Both need manual intervention, but auto-pause is fixed by stopping pushes and batching work, not by retrying. Manual triggers should be sequenced last, after all work is pushed, to avoid spending them on commits about to be superseded.
