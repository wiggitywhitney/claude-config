# Weekly Summary — 2026-W32

## Week in Review

The developer spent the week auditing and fixing a Claude Code configuration system (PRD #109), starting with infrastructure cleanup and measurement work, then discovering systemic problems in the checking tools themselves, and finishing by closing test coverage gaps and setting up CI.

The audit work kicked off on Monday with two major findings. First, a post-commit hook was failing silently because it couldn't find the API key—fixed by linking the commit-story package locally. Second, the developer completed the initial measurement phase by building a script that inventories every rule file and skill, tracking what loads in Claude Code sessions and what gets cut off by context compaction. This revealed that `rules/README.md` was loading unnecessarily in every session (costing ~3,100 tokens), that eight skills were hitting or exceeding the 5,000-token truncation cap, and that `@`-imported rules survive compaction because the platform re-reads root files from disk. The developer also restructured the entire PRD from nine sequential milestones into four ordered phases—Audit, Research, Design, and Disposal—moving all design work into a collaborative milestone where it happens with full research inputs available.

On Tuesday, the checking tools themselves turned out to be broken. A CodeRabbit review surfaced two rule files that were loading through both mechanisms simultaneously, which violated the project's own rules. But the checker and inventory script both missed this because they only scanned the global `CLAUDE.md`, not the project's separate config file. The developer fixed both tools to scan every `CLAUDE.md` in the project, which immediately surfaced the violations. This correction also revealed the always-loaded total was wrong—it should have been 70,228 bytes, not 63,619, because the project config file itself was never being counted. The developer also pivoted on the permissions problem after discovering that approved prompts leave no record in transcripts. Instead of mining 939 transcripts, they found two undocumented hooks in the binary that carry the actual data, and adopted auto mode as the provisional fix after measuring that looser permission modes actually had *higher* interrupt rates, not lower.

Wednesday brought structural fixes and deep testing work. The developer resolved a deadlock in the plan where one milestone was supposed to write findings into a spec that hadn't been created yet, introducing a handoff mechanism instead. They built an enumeration script (`scripts/audit-enumerate.sh`) with four subcommands that emit newline-delimited JSON for hooks, skills, configurations, and coupled file pairs. This uncovered that hook counts were actually 17, not 14, and repository count was 26, not 21. The developer then worked through the hook inventory, settling verdicts on ten of fifteen hooks and removing five hooks and two skills that were dead or broken. They discovered that the personal-context file had been loading unnecessarily for four months because the nightly job generating it had been failing with "Operation not permitted"—macOS shields the documents folder from scheduled tasks. The test suite grew to 373 passing tests with 50 cluster tests.

On Thursday, the developer fixed a broken merge gate hook that was confusing two failure modes. When the GitHub API call failed, it would print shell errors and claim no review existed instead of saying it couldn't verify the status. The developer restructured it to capture API output first, fail immediately if the lookup breaks, and count matches in a single pass. They also discovered a much bigger problem: the repository had 376 shell tests and four Python test suites that never ran under any automated gate—only when someone manually typed the command. Rather than add them to the local push tier (which would slow every push during review), they created a GitHub Actions workflow to run all three test suites on macOS in parallel with the existing CodeRabbit review.

Friday was mostly about documenting the CI change. The developer confirmed the workflow was set up to run each suite to completion even if an earlier one fails, so nothing gets hidden, and updated the progress log to explain the reasoning. The first CI run also served as an experiment to determine whether the fourteen failing tests were environment-specific (caused by Datadog policy and global gitignore on the developer's machine) or actual code problems.

## Highlights

- Fixed the checking tools themselves after discovering they were blind to real violations—both the rule-frontmatter checker and load-inventory script now scan every `CLAUDE.md` file in the project instead of just the global one, immediately surfacing two real double-loading violations that had been invisible.

- Corrected the always-loaded byte total from 63,619 to 70,228 bytes by including the project config file and fixing misfiled rules, fixing a 17% undercount that was in the unsafe direction for the byte budget.

- Pivoted the permissions solution from "loosen the mode" to adopting auto mode after measuring that looser modes actually had higher interrupt rates—and discovered the platform already documented this as the answer, avoiding the need to build expensive measurement infrastructure.

- Built an enumeration script with four subcommands that emit newline-delimited JSON for hooks, skills, configurations, and coupled file pairs, uncovering that hook counts were 17 (not 14) and repository count was 26 (not 21).

- Removed five dead or broken hooks and skills, including one that had been loading unnecessarily for four months because its nightly job had been failing with "Operation not permitted."

- Set up GitHub Actions CI to run all three test suites on macOS, surfacing fourteen tests that were sitting on main because they'd never been executed automatically.

## Patterns

- The checking tools kept missing violations because they only looked at part of the configuration—a pattern of incomplete scanning that repeated across multiple scripts until the developer fixed them all to read every relevant file.

- Agreed rules kept getting lost to habit: command-shape discipline, approval-prompt instructions, and TDD ordering were all documented and agreed to, then silently violated. The developer noted this as a recurring pattern that points to a general problem about enforcement versus documentation.

- The developer discovered that checking whether the platform already answers a question before building measurement infrastructure saves enormous effort—the most valuable permissions finding came from twenty minutes of reading documentation, not from the instrument built to find it.

- Multiple tools and documents drifted out of sync when they encoded the same information in multiple places—CodeRabbit CLI flags across three files, the byte budget table, milestone completion status—all instances of information that should have had a single source.
