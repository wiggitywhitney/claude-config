# Claude Code Sandbox Gotchas

- **`--dangerously-skip-permissions` and `/sandbox` are orthogonal, not substitutes.** Skip-permissions controls *whether* a tool call runs at all (no protection if skipped). The sandbox controls *what a Bash/PowerShell/Monitor command and its children can reach* once it runs, enforced by the OS (Seatbelt on macOS, bubblewrap + socat on Linux/WSL2). For unattended operation, pair both rather than relying on either alone.
- **The sandbox is off by default, even per-project.** It doesn't activate just because the platform supports it — set `sandbox.enabled: true` explicitly (globally in `~/.claude/settings.json`, or per-project).
- **The sandbox fails open by default.** If it can't start for any reason, Claude Code prints a warning and runs the command unsandboxed with no hard stop. Set `sandbox.failIfUnavailable: true` in settings for a hard gate instead of a silent fallback to unsandboxed execution.
- **A blocked sandboxed command can be re-run unsandboxed by the model, not by an automatic harness-level fallback.** Unless `sandbox.allowUnsandboxedCommands: false` is set, the model retains a `dangerouslyDisableSandbox` tool parameter it may choose to set on a retry after a sandbox block — verified 2026-09-19 (`docs/research/claude-code-permission-modes.md`, "The escape hatch is model-mediated, not a silent harness-level retry"): a blocked command stays blocked when the model is told not to retry, and only succeeds unsandboxed when the model itself re-issues the call with the parameter set. The practical risk is the same either way — a model that habitually retries defeats the sandbox just as effectively as a silent fallback would — so `sandbox.allowUnsandboxedCommands: false` is still the only setting that removes the option rather than trusting the model not to exercise it. All three keys — `sandbox.enabled: true`, `sandbox.failIfUnavailable: true`, `sandbox.allowUnsandboxedCommands: false` — are required together; any one missing leaves a real gap.
- **Fine-grained permission allowlists (`permissions.allow` in settings.json/settings.local.json) are documented as "best-effort, not a hardened shell sandbox."** Known gaps that cause prompts to fire despite a matching allow rule: exact-match vs. glob/prefix distinctions, subshells (`$(...)`), piped/chained commands, and exec wrappers (`watch`, `find -exec`). Don't expect an allowlist alone to eliminate permission prompts for unattended multi-step agent work — this is a common practical failure, not a misconfiguration.
- **Devbox provides no sandboxing whatsoever** — its isolation is Nix-based reproducible package/dependency management, not process containment. A process launched via `devbox run`/`devbox shell` has full, ordinary host filesystem and network access, identical to running the command directly. Do not treat a devbox-wrapped launcher as adding any security boundary.
- **The sandbox only covers Bash/PowerShell/Monitor commands and their children — Read, Edit, Write, WebFetch, and MCP tools are governed by the separate permission system, not the OS sandbox, at all.** Pairing skip-permissions with the sandbox contains shell-executed actions only; a file edit or network call made directly through a non-Bash tool is fully unrestricted once permissions are skipped, regardless of sandbox settings.
- **`sandbox.credentials` sub-fields are `files` and `envVars`; each entry's `mode` is `deny` or `mask` — `allow` is not a real value.** Don't invent an `allow` mode.
- **Repo-root committed `.claude/settings.json` sandbox settings apply to every session opened in that repo, including a developer's own interactive terminal use — there is no automatic "only unattended invocations" scoping.** To scope sandbox settings to one specific launch without affecting other sessions in the same repo, use `claude --settings '{"sandbox": {...}}'` on that invocation instead of (or in addition to) a committed settings file.
- Native support: macOS (Seatbelt) and Linux/WSL2 (bubblewrap). Native Windows and WSL1 are unsupported.
- The sandbox's network isolation is proxy-based (checks an allowlist, returns 403 on denial); the kernel-level backstop only covers tools that ignore proxy env vars, so it isn't a uniform kernel-level network block for every tool.
- Anthropic's own recommended defense-in-depth pattern for fully unattended operation is a devcontainer with a non-root user layered on top of the sandbox — evaluate whether that's proportionate per-project rather than assuming it's required; a single-operator local setup may reasonably decline it the same way other OS-level isolation layers get declined for disproportionate effort relative to risk.
